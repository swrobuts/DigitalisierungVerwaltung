1. Warum trotz UE0 noch ein Webformular?

UE0 (PDF-Upload mit KI-OCR) hat einen klaren Vorteil: die Bürger:in muss nichts Neues lernen. Aber er hat auch zwei harte Grenzen:

  • Die Bürger:in braucht weiterhin das PDF — wer keinen Drucker oder Scanner hat, ist raus.
  • Keine Live-Validierung beim Ausfüllen — Tippfehler fallen erst in der Sachbearbeitung auf.
  • Das PDF ist deutsch — Migrant:innen ohne Deutsch-Kenntnisse haben kaum Zugang.

UE1 löst genau diese drei Punkte und bietet zusätzlich:

  • FB-spezifischen Wizard (nur relevante Felder werden angezeigt)
  • Sticky-Progress-Bar mit klarem Fortschritts-Feedback
  • Anlagen-Upload (Wochenplan, Helferliste, Mietvertrag) direkt im Formular
  • Mehrsprachigkeit — DE/TR vollständig, IT/RU/FR als β-Marker
💡 Strategische Sicht: UE0 und UE1 sind parallele Eingangskanäle. Die Bürger:in entscheidet selbst, was zu ihrer Situation passt. UE0 = „ich kenne das PDF schon, lass mich kurz hochladen". UE1 = „ich starte direkt am Computer / Handy".

2. Der Multi-Förderbereich-Wizard

Die Würzburger Altenhilfe-Förderrichtlinie kennt vier Förderbereiche, davon einer mit vier Varianten:

FB I — Aufbau niedrigschwelliger Angebote (Neu-Projekte)
FB II — Pauschale Förderung Ehrenamt (Helferlisten)
FB III A — Mehrgenerationenhaus
FB III B — Begegnungszentrum
FB III C — Seniorenkreis (≥10/20/40 Treffen)
FB III D — Quartiersmanagement
FB IV — Schwerpunkt (formlos, PDF reicht)

Der Wizard blendet ein, was nötig ist: wer FB III · Variante C wählt, sieht nur die Seniorenkreis-Felder (Treffen-Anzahl, Teilnehmer-Schnitt). Wer FB I wählt, sieht Projekt-Titel, Personal- und Sachkosten.

Architektur-Trick: Die FB-Konfiguration lebt als Daten-Modul in packages/foerderbereiche/ — pro FB eine TypeScript-Datei mit Feld-Definitionen. Kein Hardcoding in UE1/UE2/UE3. Wer eine neue Variante hinzufügt, ändert nur eine Datei.

3. Live-Validation, Sticky-Progress, i18n

Live-Validation

Drei Sorten Prüfung im Frontend:

  • Field-Level: IBAN (Mod-97), E-Mail (RFC), PLZ (5 stellig), Datum (ISO 8601). Pure Functions, getestet mit Vitest.
  • Cross-Field: z.B. „Wenn keine eigenen Räume → Miete muss > 0 sein". Regelmäßig erweitert bei neuen FBs.
  • Server-Re-Validation in der Edge Function als Defense-in-Depth — Frontend könnte manipuliert werden.

Sticky-Progress-Bar

Vier sichtbare Phasen oben: 

1. FB-Wahl  →  2. FB-Details  →  3. Anlagen  →  4. Bestätigung
[✓ erledigt] [● aktiv] [○ offen] [○ offen]

Klick auf einen erledigten Step springt zurück. Vorwärts-Sprung ist gesperrt — Bürger:in muss linear arbeiten.

i18n-Stack

Sprach-Picker oben rechts mit fünf Sprachen. DE+TR komplett übersetzt (Stadt Würzburg hat hohen Anteil türkisch-stämmiger Bevölkerung). IT/RU/FR sichtbar als β, fallen aber bei fehlenden Keys auf Deutsch zurück — und ein gelbes Banner sagt das offen.

⚠️ Ehrlichkeit beim i18n: Eine β-Sprache, die transparent gekennzeichnet ist, hilft schon — sie signalisiert, dass das Amt die Sprache anstrebt. Lügt sie aber „vollständig" und ist es nicht, frustriert das mehr als wenn der Picker sie gar nicht erst zeigt.

4. Submit, Storage, Datenfluss

Der Submit geht nicht direkt vom Browser in die DB (auch wenn RLS das technisch erlauben würde), sondern über eine Edge Function: 

POST /functions/v1/submit-antrag
  ├── server-side Validation (Defense-in-Depth)
  ├── IP + User-Agent capturen (DSGVO-relevante Audit-Trail)
  ├── INSERT apl.antraege (Antragsnummer kommt aus DB-Trigger)
  ├── Storage-Upload aller Belege parallel
  └── bei Upload-Fehler: full rollback (DELETE antrag + Storage cleanup)

Output: APL-2026-FBIII-A1B2C3 Antragsnummer + URL zur Bestätigungs-Seite.

💡 Architektur-Pattern: Edge Function als „API-Gateway in den eigenen Daten". Kein direct browser-to-DB, auch wenn RLS das schützen würde. So bleibt der Anon-Key „lese-only-fähig" und alle schreibenden Operationen sind auditierbar.

Verständnis-Quiz

Vier Fragen, je 1 richtige Antwort. Klicke eine Option für Feedback.

1. Wo lebt der Form-State von UE1?

  • Im React-Redux-Store
  • In einem zentralen state.ts-Modul mit subscribe-Pattern
  • Nur im DOM
  • Wird bei jeder Eingabe sofort in Supabase persistiert

2. Was passiert bei t("nicht.existierender.key")?

  • Exception
  • Leerer String
  • Fallback auf DE, sonst Key selbst
  • Sofort ein gelbes Warn-Banner

3. Warum geht der Submit über eine Edge Function statt direkt browser→DB?

  • Weil RLS nicht ausreicht
  • Weil sonst der ANON-Key gestohlen werden könnte
  • Weil Supabase keine direkten Inserts erlaubt
  • Für server-side Validation + IP/UA-Capture + atomarität mit Storage

4. Wie sieht der Wizard sich verändernde FB-Felder?

  • Über Daten-Module in packages/foerderbereiche/
  • Hardcoded in jedem View pro FB
  • Vom Server geladen per AJAX
  • Aus einer JSON-API generiert
